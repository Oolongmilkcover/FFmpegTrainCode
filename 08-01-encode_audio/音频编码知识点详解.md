# 音频编码（PCM → AAC）知识点详解

> 配套源码：`main.cpp`（注释里的「【知识点 N】」与本文编号一一对应）
> 环境：Qt 6.11.0 (MinGW 13.1.0) + FFmpeg 8.1（libavcodec 62 / libavutil 60）
> 源码语言：**C++17**。三个工程（08-01 音频编码 / 08-02 视频编码 / 08-03 封装）
> 统一使用同一套 C++ 风格 + CMake 配置，便于直接迁进 pusher。
> 本文只讲**音频编码本身**：每一步在做什么、API 参数什么含义、为什么这么调、坑在哪。
>
> 转成 C++ 时改了什么（以及为什么）：
> | C 写法 | C++17 写法 | 原因 |
> | --- | --- | --- |
> | `#include <stdio.h>` | `extern "C" { #include <cstdio> }` 风格 | FFmpeg 是 C API，C++ 里必须包 `extern "C"` |
> | `fprintf/printf/malloc/free` | `std::fprintf/std::printf/std::malloc/std::free` | 落在 `std` 命名空间 |
> | `char*` 存路径 | `std::string` | 免去手动管理，且 `EncodeConfig` 可带默认值（不用 memset） |
> | `goto cleanup` | 立即执行 lambda + `return` | **C++ 禁止 goto 跳过带初始化的变量声明** |
> | `(uint8_t*)ptr` | `static_cast<uint8_t*>(ptr)` | C++ 不允许 `void*` 隐式转换；显式转换也更醒目 |
> | `NULL` | `nullptr` | 类型安全 |
> | `NULL` 装 `const void*` 出参 | `nullptr` + `static_cast<T*>` | 泛型出参必须显式转回具体类型 |
>
> **验证**：C++ 版输出的 `.aac` 与 C 版**逐字节完全一致**（MD5 相同），
> 说明这次转换是纯粹的语法/风格迁移，没有改变任何行为。

## 0. 从 PCM 到 AAC：完整数据流

```
磁盘                        内存                  编码器内部              输出
──────────                ──────────            ──────────            ──────
裸 PCM 文件      读      写   AVFrame      送    AAC 编码器      取     AVPacket
交错 L R L R   ────▶   ────▶ 分平面 L|R   ────▶  攒够1024点    ────▶   裸 AAC 帧
s16le/f32le              fltp                 │ 做 MDCT              │
                                              │ 量化 + 熵编码         │
                                              ▼                     ▼
                                    每次 1024 个采样点        手写 7B ADTS 头
                                    (frame_size)             + 裸数据写文件
```

**三个必须先建立的观念**

| 观念 | 内容 |
| --- | --- |
| **PCM 不含格式信息** | 它就是一堆采样点字节。同样 1925956 字节，按 `s16` 解释是 10 秒，按 `f32` 解释是 5 秒。所以读裸 PCM 必须由调用方提供「采样率 + 声道数 + 采样格式」三个参数。 |
| **编码器对输入有要求** | 不是给你什么都能编。native AAC 只吃 `AV_SAMPLE_FMT_FLTP`；ffmpeg 命令行只能导出 packed PCM。中间必须有一道格式转换。 |
| **编码器有内部延迟** | AAC 要攒够 1024 点才能做一次 MDCT。所以「送 1 帧」不等于「收 1 个包」，第一次 `send` 之后一个包都拿不到。 |

## 1. 音频参数四要素

编码器配置里最核心的就是这四个数字，缺一不可。

### 1.1 采样率 sample_rate（Hz）

每秒采多少个点。它决定了**能表示的最高频率**（奈奎斯特定理）：

```
可表示的最高频率 = 采样率 / 2
```

| 采样率 | 上限频率 | 典型用途 |
| --- | --- | --- |
| 8000 | 4000 Hz | 电话 |
| 16000 | 8000 Hz | 宽带语音、VoIP |
| 22050 | 11025 Hz | 低质量音频 |
| 44100 | 22050 Hz | CD（历史原因来自 PAL 视频行频） |
| **48000** | **24000 Hz** | 视频标准（本项目用的） |
| 96000 | 48000 Hz | 高解析音频、录音棚 |

人耳上限约 20000 Hz，所以 44100/48000 已经覆盖全部可听范围。

> **注意**：AAC 只支持 **13 个固定采样率**（7350~96000）。程序实测输出：
> `96000 88200 64000 48000 44100 32000 24000 22050 16000 12000 11025 8000 7350`
> 传 44101 这种值会 `avcodec_open2` 失败。这是 AAC 规范锁死的，不是 FFmpeg 的限制。

### 1.2 【知识点 2.1 / 12 / 19】声道数 / 声道布局 ch_layout

**声道布局描述的不只是「几个声道」，还有「分别是什么、按什么顺序排」。**

| 布局 | 声道数 | 含义与顺序 |
| --- | --- | --- |
| mono | 1 | 单声道 |
| stereo | 2 | 左(FL) / 右(FR) |
| 2.1 | 3 | FL / FR / LFE |
| 5.1 | 6 | FL / FR / FC / LFE / BL / BR |
| 7.1 | 8 | 在 5.1 基础上加 SL / SR |

为什么顺序重要？因为 2 声道的 `stereo`（FL/FR）和 2 声道的 `downmix`（SL/SR）含义不同，
6 声道的 `5.1` 和 `6.0` 排布也不同。给错了，编码器的声道耦合决策会错，解码端下混也会错。

`AVChannelLayout` 结构体（FFmpeg 8.1）：

```c
typedef struct AVChannelLayout {
    enum AVChannelOrder order;   // 顺序语义
    int                 nb_channels;  // 声道数
    union {
        uint64_t         mask;   // order == NATIVE 时的位掩码
        AVChannelCustom *map;    // order == CUSTOM 时的逐声道表（持有堆内存）
    } u;
    void *opaque;
} AVChannelLayout;
```

`order` 的四种取值：

| order | 含义 | 举例 |
| --- | --- | --- |
| `AV_CHANNEL_ORDER_NATIVE` | 标准布局，用掩码描述 | stereo、5.1 |
| `AV_CHANNEL_ORDER_UNSPEC` | 只知道声道数，不知道每路是什么 | 分析未知音频时 |
| `AV_CHANNEL_ORDER_CUSTOM` | 逐声道自定义，`u.map` 指向堆数组 | 特殊麦克风阵列 |
| `AV_CHANNEL_ORDER_AMBISONIC` | 全景声 | VR / 空间音频 |

**三条必须记住的铁律**

1. **比较只能用 `av_channel_layout_compare(a, b)`**，返回 0 表示相等。
   - 不能写 `a == b`（结构体不支持比较运算）
   - 更不能 `memcmp`（里面有 `opaque`/`map` 指针，同布局不同指针会误判不等）

2. **复制只能用 `av_channel_layout_copy(dst, src)`**，不能写 `dst = src`。
   因为 `CUSTOM` 布局的 `u.map` 指向堆内存，浅拷贝会让两个结构体指向同一块内存 →
   **double free**。官方原话：*"Copying an AVChannelLayout via assigning is forbidden"*。

3. **谁分配谁释放**
   | 对象 | 谁负责 uninit |
   | --- | --- |
   | `codec_ctx->ch_layout` | `avcodec_free_context()` |
   | `frame->ch_layout` | `av_frame_free()` |
   | 自己声明的栈上布局 | **自己调 `av_channel_layout_uninit()`** |

**常用构造函数**

```c
av_channel_layout_default(&l, 2);                       // 按声道数取标准布局 → stereo
av_channel_layout_from_mask(&l, AV_CH_LAYOUT_STEREO);   // 从位掩码构造
av_channel_layout_from_string(&l, "5.1(side)");         // 从字符串解析
av_channel_layout_describe(&l, buf, sizeof(buf));       // 转可读字符串（打日志用）
av_channel_layout_check(&l);                            // 校验合法性
av_channel_layout_uninit(&l);                           // 释放
```

> **原型常量名字只差一个字母，别搞混**：
> `AV_CH_LAYOUT_STEREO` 是 `uint64_t` 位掩码（值 0x3），
> `AV_CHANNEL_LAYOUT_STEREO` 是 `AVChannelLayout` 结构体初始化器。

### 1.3 【知识点 6 / 13】采样格式 sample_fmt —— packed vs planar

这是音频编码里最容易糊涂的概念。

同一个立体声瞬间的两个采样点，有两种内存排布：

```
packed（交错 / interleaved）              planar（分平面）
  内存: L0 R0 L1 R1 L2 R2 L3 R3 ...       内存: data[0] → L0 L1 L2 L3 ...
  单块内存                                      data[1] → R0 R1 R2 R3 ...
  data[0] 指向全部，data[1] = NULL         每声道一块独立内存
  典型: s16 / s32 / flt                    典型: fltp / s16p（末尾带 p）
```

判断方法：

```c
av_sample_fmt_is_planar(fmt);   // 返回 1 表示 planar
```

**采样点类型对照表**（注意 ffmpeg 命令行名与 `AVSampleFormat` 名的关系）：

| `ffmpeg -f` 名 | AVSampleFormat | 每点字节 | 布局 | 数值范围 |
| --- | --- | --- | --- | --- |
| `u8` | `AV_SAMPLE_FMT_U8` | 1 | packed | 0 ~ 255（无符号，有偏置） |
| `s16le` | `AV_SAMPLE_FMT_S16` | 2 | packed | -32768 ~ 32767 |
| `s32le` | `AV_SAMPLE_FMT_S32` | 4 | packed | -2^31 ~ 2^31-1 |
| `f32le` / `flt` | `AV_SAMPLE_FMT_FLT` | 4 | packed | -1.0 ~ 1.0 |
| `f64le` / `dbl` | `AV_SAMPLE_FMT_DBL` | 8 | packed | -1.0 ~ 1.0 |
| `s16p` | `AV_SAMPLE_FMT_S16P` | 2 | **planar** | -32768 ~ 32767 |
| `fltp` | `AV_SAMPLE_FMT_FLTP` | 4 | **planar** | -1.0 ~ 1.0 |

> **为什么名字里没有 `le`/`be`？**
> 因为文件里的字节序就是本机字节序（x86 是小端），FFmpeg 内部不做字节序转换。
> 只有跨平台传文件时才需要考虑大小端。

> **为什么 AAC 用 float 而不是 int16？**
> MDCT 变换和量化都在浮点域做，精度更高。编码器内部即使收 s16 也要先转成浮点，
> 所以直接喂 fltp 可以省掉一次转换。

**本项目实测**：`aac` 编码器只支持一个采样格式 —— `fltp`。

### 1.4 【知识点 10】码率 bit_rate

单位是 **bit/s**，不是 Byte/s。

```c
codec_ctx->bit_rate = 128 * 1024;   // 131072 bit/s = 128 kbps
```

| 码率 | 音质感知 |
| --- | --- |
| 64 kbps | 立体声有可闻损失 |
| 96 kbps | 基本可用 |
| **128 kbps** | **透明，大部分人听不出与原始的区别**（本项目选的） |
| 192 kbps | 边际收益很小 |
| 256 kbps+ | 对绝大多数内容无意义 |

> **实际码率会波动**：ffprobe 实测本项目输出是 130.2 kbps，而设定值是 128 kbps。
> 这是 ABR（平均码率）策略的正常表现 —— 编码器在复杂段落多给比特、
> 简单段落少给，整体贴近目标值。

### 1.5 【知识点 11】profile —— AAC 的「档次」

`profile` 的值就是 AAC 规范里 `audioObjectType - 1`：

| 宏 | 值 | audioObjectType | 说明 |
| --- | --- | --- | --- |
| `AV_PROFILE_AAC_MAIN` | 0 | 1 | 多了反向预测，几乎没人用 |
| **`AV_PROFILE_AAC_LOW`** | **1** | **2** | **AAC-LC，最常用，兼容性最好**（本项目） |
| `AV_PROFILE_AAC_SSR` | 2 | 3 | 低延迟场景 |
| `AV_PROFILE_AAC_LTP` | 3 | 4 | 长时预测 |
| `AV_PROFILE_AAC_HE` | 4 | 5 | HE-AAC (SBR)，低码率下重建高频 |
| `AV_PROFILE_AAC_HE_V2` | 28 | 29 | HE-AACv2 (SBR+PS)，更低码率 |
| `AV_PROFILE_AAC_LD` | 22 | 23 | 低延迟，通信场景 |

**关键联系**：ADTS 头里的 `profile` 字段（2 bit）填的就是这个值（减 1 之后）。
所以 LC 在 ADTS 头里写 1，正好等于 `AV_PROFILE_AAC_LOW`。

## 2. 完整调用流程与每步的 API 细节

### 步骤 1：【知识点 8】查找编码器

```c
const AVCodec *codec = avcodec_find_encoder(AV_CODEC_ID_AAC);
// 或
const AVCodec *codec = avcodec_find_encoder_by_name("aac");
```

| 方式 | 特点 |
| --- | --- |
| `avcodec_find_encoder(id)` | 按格式 ID 找，返回注册表里**第一个匹配**的实现。同一 ID 可能有多个（`aac`/`libfdk_aac`/`aac_mf`/`aac_at`），返回哪个取决于编译顺序，**不可控** |
| `avcodec_find_encoder_by_name(name)` | 按 `AVCodec.name` 精确找，结果**可控**。生产代码推荐 |

- 返回值指向 libavcodec 的**全局静态注册表**，不需要也不允许 `free`
- 返回 `NULL` 表示这个 FFmpeg 编译时没启用该编码器
- 用 `ffmpeg -encoders | findstr aac` 查本机有哪些
- 本机 FFmpeg 8.1 是 `--disable-libfdk-aac` 编译的，只有 `aac` 和 `aac_mf`

**有用的 AVCodec 字段**

```c
codec->name          // "aac"
codec->long_name     // "AAC (Advanced Audio Coding)"
codec->capabilities  // 位标志集合
```

`capabilities` 里要知道的几个：

| 标志 | 含义 |
| --- | --- |
| `AV_CODEC_CAP_DELAY` | **编码器有内部延迟**，必须 flush 才能拿到全部数据 |
| `AV_CODEC_CAP_EXPERIMENTAL` | 实验性编码器，需要显式降 `strict_std_compliance` 才允许打开 |
| `AV_CODEC_CAP_VARIABLE_FRAME_SIZE` | 接受任意 `nb_samples`，不强制 `frame_size` |

> 本项目实测：`aac` 的 `capabilities = 0x62`，含 `AV_CODEC_CAP_DELAY`。

### 步骤 2：【知识点 9】分配上下文

```c
AVCodecContext *ctx = avcodec_alloc_context3(codec);
```

它做三件事：

1. 分配 `AVCodecContext`
2. 调 `avcodec_get_context_defaults3()`，用 codec 的信息填默认值
   —— **`codec_id` / `codec_type` 已经填好了，不需要手动赋值**
3. 按 `codec->priv_data_size` 分配**私有数据区**（编码器自己的参数存在这里）

> 旧的 `avcodec_alloc_context()` 不带 codec 参数，所有字段都要手填，容易漏，已废弃。
> **永远用 `alloc_context3`。**

### 步骤 3：设置参数

顺序建议：**先设参数 → 再查能力 → 再 open**。

### 步骤 4：【知识点 2 / 14】查编码器能力

```c
int avcodec_get_supported_config(const AVCodecContext *avctx,   // 可为 NULL
                                 const AVCodec        *codec,   // 为 NULL 则用 avctx->codec
                                 enum AVCodecConfig    config,  // 查哪一项
                                 unsigned              flags,   // 保留，填 0
                                 const void          **out_configs,      // 出参：数组首地址
                                 int                  *out_num_configs); // 出参：个数，可为 NULL
```

`enum AVCodecConfig` 与返回数组的对应关系：

| config | 数组元素类型 | 哨兵值 |
| --- | --- | --- |
| `AV_CODEC_CONFIG_SAMPLE_FORMAT` | `enum AVSampleFormat` | `AV_SAMPLE_FMT_NONE` |
| `AV_CODEC_CONFIG_SAMPLE_RATE` | `int` | `0` |
| `AV_CODEC_CONFIG_CHANNEL_LAYOUT` | `AVChannelLayout` | `{0}`（`nb_channels == 0`） |
| `AV_CODEC_CONFIG_PIX_FORMAT` | `enum AVPixelFormat` | `AV_PIX_FMT_NONE` |
| `AV_CODEC_CONFIG_FRAME_RATE` | `AVRational` | `{0, 0}` |

**四个必须注意的细节**

1. **数组用哨兵结尾，不是靠 `out_num_configs`**。必须按哨兵遍历。
   这是 libavcodec 的一贯风格，官方示例 `encode_audio.c` 至今也是这么写的。

2. **`*out_configs == NULL` 不是失败，而是「不做限制，全都能用」**。
   这时应直接判定为支持。

3. **出参是 `const void *`**，因为一个函数要返回 7 种不同的数组类型。
   取出来必须显式转换：
   ```c
   const enum AVSampleFormat *p = (const enum AVSampleFormat *)cfgs;
   ```

4. **为什么不能跳过这一步直接 open？**
   `avcodec_open2` 失败时只给一个笼统的 `AVERROR(EINVAL)`，
   你根本不知道是采样格式、采样率、还是声道布局出了问题。
   提前查能力能把错误定位到具体参数。

### 步骤 5：【知识点 16】打开编码器 —— `avcodec_open2`

```c
int avcodec_open2(AVCodecContext *avctx, const AVCodec *codec, AVDictionary **options);
```

它做的事：

1. 校验所有参数组合是否合法（不合法返回负错误码）
2. 打开编码器私有上下文（分配 FFT/MDCT 表、量化表、窗函数表等）
3. **回填 `frame_size`** —— 告诉你「每次要喂多少个采样点」
4. 回填 `delay` / `initial_padding`
5. 应用 `AVDictionary` 里的私有选项

**第三个参数是编码器私有选项**，例如：

```c
AVDictionary *opts = NULL;
av_dict_set(&opts, "aac_coder", "fast", 0);   // twoloop(默认) / fast
av_dict_set(&opts, "aac_ms",    "1",    0);   // 强制 M/S 立体声编码
if (avcodec_open2(ctx, codec, &opts) < 0) { ... }
av_dict_free(&opts);                          // ★ 用完必须 free
```

查看某个编码器有哪些选项：`ffmpeg -h encoder=aac`

本机实测 `aac` 的选项：
```
aac_coder   <int>    0=twoloop(默认) 1=fast     编码算法
aac_ms      <boolean>                           强制 M/S 立体声
aac_is      <boolean> 默认 true                 强度立体声
aac_pns     <boolean> 默认 true                 感知噪声替换
aac_tns     <boolean> 默认 true                 时域噪声整形
aac_pce     <boolean> 默认 false                强制使用 PCE
```

> **`strict_std_compliance`**：如果编码器带 `AV_CODEC_CAP_EXPERIMENTAL`，
> 必须在 open 前设 `ctx->strict_std_compliance = FF_COMPLIANCE_EXPERIMENTAL`。
> 本项目用的 `aac` 不带这个标志，所以不需要（代码里留了防御性检查）。

### 步骤 6：【知识点 26】frame_size 的含义 ★

**AAC 的 `frame_size` 恒为 1024。**

```
时域: 1024 个采样点  ──MDCT──▶  1024 个频域系数  ──量化+熵编码──▶  一个 AAC 帧
      @48kHz = 21.33 ms
```

所以：

- 送 1024 个采样点 → 吐出 1 个包
- 送 4096 个采样点 → 吐出 4 个包
- `frame_size` 在 `avcodec_open2` 之前是 0，**之后才有意义**（本程序把这个对比打印出来了）

> 不同编码器的 `frame_size` 不同：MP3 是 1152，Opus 是 960（48kHz），
> MP2 是 1152。所以**绝对不能硬编码 1024**，必须读 `ctx->frame_size`。
> 少数编码器带 `AV_CODEC_CAP_VARIABLE_FRAME_SIZE`，可以任意大小。

### 步骤 7：【知识点 16.1】delay vs initial_padding

这两个字段容易混淆，含义完全不同：

| 字段 | 含义 | 影响 |
| --- | --- | --- |
| `delay` | 编码器为了做变换需要「往前看」多少采样点 | 输出滞后 |
| `initial_padding` | 编码器开头插入多少 priming 采样点 | **PTS 从 `-initial_padding` 开始** |

**本项目实测**：`aac` 报 `delay = 0`、`initial_padding = 1024`，
所以第一个包的 `pts = -1024` —— 正好对上。

这解释了为什么「送 471 帧，收 472 个包」：多的那个就是 priming 帧。

> 不同编码器报法不同：lame(MP3) 报 `delay`，AAC 报 `initial_padding`。
> 写通用封装时两个都要考虑。

## 3. AVFrame：装原始采样

### 3.1 【知识点 18】一帧音频由三要素完全确定

```c
frame->nb_samples = codec_ctx->frame_size;                  // 1024
frame->format     = codec_ctx->sample_fmt;                  // FLTP
av_channel_layout_copy(&frame->ch_layout, &codec_ctx->ch_layout);  // stereo
```

内存占用：

```
总字节 = av_get_bytes_per_sample(format) × nb_channels × nb_samples
       = 4 × 2 × 1024 = 8192 字节          （fltp / stereo / 1024）
```

但这 8192 字节**分在两块内存**里（每块 4096），即 `data[0]` 和 `data[1]`。

### 3.2 【知识点 20】av_frame_get_buffer —— 分配数据内存

```c
int av_frame_get_buffer(AVFrame *frame, int align);
```

- **`align` 传 0 表示用默认对齐**（通常 32 或 64 字节）
- 对齐的目的是让 SIMD 指令（SSE/AVX）能一次读整块内存，不对齐会掉性能甚至崩
- 只有特殊场景（如设备要求紧凑排列）才手动指定

它根据 `nb_samples` / `format` / `ch_layout` 自动：
- 为 planar 格式分配 `nb_channels` 个独立 buffer
- 填好 `frame->data[i]` 指针和 `frame->linesize[0]`
- 内存是引用计数的（`AVBufferRef`），`av_frame_free` 时自动释放

> **调用前必须先把那三个字段设好**，否则算出来的大小是错的。

### 3.3 【知识点 21】linesize 的正确理解

| 格式 | `linesize[0]` 的含义 |
| --- | --- |
| packed | 一行（所有声道）的字节数 |
| planar | 一行（**单个**声道）的字节数，各平面等长 |

为什么会有「行」？因为对齐要求可能带来 padding。本项目每声道需要 `4×1024 = 4096`
字节，正好对齐，所以 `linesize[0] == 4096`。

> ⚠ **容易踩的坑**：对音频，**不要用 `linesize[1]` 当「第 2 声道的大小」**。
> `av_frame_get_buffer` 对音频只把 `data[i]` 填好，`linesize` 只在 `linesize[0]`
> 里有意义。用 `linesize[1]` 算偏移会读到未初始化值。
> **正确做法**：平面字节数 = `nb_samples × av_get_bytes_per_sample(format)`。

### 3.4 【知识点 24】av_frame_make_writable —— 为什么每帧写之前都要调

```c
ret = av_frame_make_writable(frame);
```

编码器可能持有上一帧的引用（引用计数）。如果 buffer 还被编码器引用着，直接写会：

1. 破坏编码器正在用的数据 → 编出来的声音是错的
2. 数据竞争（多线程编码时）

`av_frame_make_writable` 检查引用计数：

| 引用情况 | 行为 | 开销 |
| --- | --- | --- |
| 只有你一个人用 | 什么都不做，直接返回 | 零 |
| 还有别人引用 | 偷偷重新分配一块新 buffer，拷旧数据过来 | 一次内存分配 + 拷贝 |

**返回值必须检查**：为负说明重新分配失败，此时 frame **不可写**。

### 3.5 【知识点 25】av_samples_fill_arrays —— 把数据「挂」到 frame 上

```c
int av_samples_fill_arrays(uint8_t **audio_data,   // 出参：frame->data
                           int *linesize,          // 出参：frame->linesize
                           const uint8_t *buf,     // 你的 PCM 内存
                           int nb_channels,
                           int nb_samples,
                           enum AVSampleFormat sample_fmt,
                           int align);
```

**最重要的一点：它不拷贝数据**，只是把 `buf` 的地址按格式拆开：

```
packed  →  buf 整体挂到 data[0]，data[1] = NULL
planar  →  buf 按 nb_samples 切分
           data[0] = buf
           data[1] = buf + nb_samples × 每点字节
           data[2] = buf + 2 × nb_samples × 每点字节
           ...
```

**后果**：`pcm_buf` / `pcm_temp_buf` 的生命周期必须覆盖到
`avcodec_send_frame()` **返回之后**。

## 4. packed → planar 转换

### 4.1 为什么必须转

| 来源 | 格式 |
| --- | --- |
| `ffmpeg -f f32le` 导出的 PCM | **packed**（交错） |
| `ffmpeg -f f32le`（同上，命令行只能导 packed） | packed |
| native `aac` 编码器要求 | **FLTP（planar）** |

所以中间必须有一道转换，这是所有 FFmpeg 音频编码入门代码都要做的。

### 4.2 【知识点 6】做法 A：手写转换（理解用）

```c
static void f32le_convert_to_fltp(const float *f32le, float *fltp, int nb_samples)
{
    float *fltp_l = fltp;                 // 左声道从头部开始
    float *fltp_r = fltp + nb_samples;    // 右声道偏移 nb_samples 个 float
    for (int i = 0; i < nb_samples; i++) {
        fltp_l[i] = f32le[i * 2];         // packed 下标 2i   → planar 左
        fltp_r[i] = f32le[i * 2 + 1];     // packed 下标 2i+1 → planar 右
    }
}
```

- **优点**：直观，能看清 planar 排布，零依赖
- **缺点**：只能处理「2 声道 + f32le + 采样率不变」
- **调试技巧**：把其中一行注释掉，可以听出「只有一边有声音」的效果

### 4.3 【知识点 7】做法 B：libswresample（生产代码唯一正确做法）

swr 一次能同时完成**三种**转换：

| 维度 | 转换内容 |
| --- | --- |
| 采样格式 | `s16 ↔ flt ↔ fltp`（含 packed/planar 布局变化） |
| 声道布局 | `mono ↔ stereo ↔ 5.1`（含上混/下混矩阵） |
| 采样率 | `44100 ↔ 48000`（含抗混叠滤波） |

标准三步：

```c
SwrContext *swr = NULL;
AVChannelLayout in_layout;

av_channel_layout_default(&in_layout, in_channels);   // 构造输入布局

swr_alloc_set_opts2(&swr,
                    &enc_ctx->ch_layout, enc_ctx->sample_fmt, enc_ctx->sample_rate,  // 目标
                    &in_layout,          in_fmt,             in_rate,                // 源
                    0, NULL);
av_channel_layout_uninit(&in_layout);   // ★ 栈上布局用完必须释放

swr_init(swr);                          // 计算滤波器系数，较耗时，别放循环里

// 每次转换：
int out_samples = swr_convert(swr, frame->data, out_count,
                              (const uint8_t **)&pcm_buf, in_samples);
frame->nb_samples = out_samples;        // ★ 必须用返回值！
...
swr_free(&swr);
```

**三个必须注意的细节**

1. **`swr_alloc_set_opts2` 的第一个参数是二级指针**，必须传 `&swr`。
   它内部会自己分配 `SwrContext`。

2. **输入的 `AVChannelLayout` 要单独构造**，不能直接复用编码器的
   （编码器要求 48000/2ch，源可能是 44100/1ch）。

3. **`swr_convert` 的返回值是实际输出采样点数，不等于输入采样点数**。
   因为 swr 内部带 **FIFO**：当输入/输出采样率不同，或内部滤波器需要历史数据时，
   它会把尾巴缓存起来下次再吐。
   ```c
   frame->nb_samples = nb_in_samples;              // ✗ 错
   frame->nb_samples = swr_convert(...);           // ✓ 对
   ```
   想知道「最多可能吐出多少」，用 `swr_get_out_samples(swr, in_samples)`。

**本项目实测输出**：

```
输入 PCM : 48000_2_s16le.pcm
  48000 Hz, 2 声道, s16 (packed 交错)
swr 已建立：s16/2ch/48000Hz  ->  fltp/2ch/48000Hz
```

### 4.4 swr 参数速查

```c
// 旧 API（已废弃，参数是 uint64_t 掩码）
swr_alloc_set_opts(swr, out_ch_layout, out_fmt, out_rate,
                        in_ch_layout,  in_fmt,  in_rate, log_offset, log_ctx);

// 新 API（用这个）
swr_alloc_set_opts2(&swr, &out_layout, out_fmt, out_rate,
                          &in_layout,  in_fmt,  in_rate, 0, NULL);
```

## 5. 【知识点 4】编码循环：send / receive 配对规则

这是 libavcodec **唯一正确**的编码 API 用法。

```c
avcodec_send_frame(ctx, frame);              // 送 1 次
while (1) {
    ret = avcodec_receive_packet(ctx, pkt);  // 收 N 次
    if (ret == AVERROR(EAGAIN) || ret == AVERROR_EOF)
        break;                               // 正常结束
    if (ret < 0) { /* 真错误 */ }
    /* 消费 pkt */
}
```

### 六条必须理解的规则

**规则 1：为什么是 1 送 N 收，而不是「送一帧得一帧」？**

编码器内部有缓存和 look-ahead。本项目实测：

```
送出 frame[1]: nb_samples=1024 pts=0
  (编码器缓冲中：本次没有输出包，需要更多输入)     ← 第 1 次 send 一个包都没有
送出 frame[2]: nb_samples=1024 pts=1024
  pkt[ 1] size= 284 pts=-1024    dts=-1024    duration=1024   ← priming 帧
送出 frame[3]: nb_samples=1024 pts=2048
  pkt[ 1] size= 319 pts=0        dts=0        duration=1024   ← 真实音频第 1 帧
```

「packet 数」和「frame 数」对不上是**完全正常**的。

**规则 2：`AVERROR(EAGAIN)` 不是错误**

| 返回值 | 含义 | 处理 |
| --- | --- | --- |
| `AVERROR(EAGAIN)` | 现在没有包，请再送输入 | 正常，break 出去继续送 |
| `AVERROR_EOF` | 冲刷完毕，以后也不会再有了 | 正常，结束 |
| 其它 `< 0` | 真错误 | 用 `av_strerror` 翻译后报错 |

**规则 3：冲刷（flush）—— send 一个 NULL frame**

```c
encode(ctx, NULL, pkt, outfile, write_adts);
```

编码器会把内部残留的采样点全部编码出来。本项目实测：

```
文件读取完毕
冲刷编码器（send NULL）...
  pkt[ 1] size= 547 pts=480256   dts=480256   duration=1024  ← 含尾部 209 个点
  pkt[ 2] size=   7 pts=481280   dts=481280   duration=209   ← 纯 padding，补齐
  冲刷完成：共 2 个包，首包 pts=480256
```

> **不冲刷的后果**：末尾约 21 ms 被截掉，听感上是「最后一个音被切断」。

**规则 4：`avcodec_receive_packet` 内部会 `av_packet_unref(pkt)`**

它的第一步就是「把你给我的 pkt 清空，我要往里填新数据」。带来两个后果：

- 循环里**不需要**手动 `av_packet_unref(pkt)`（官方示例里那句是冗余的、无害的）
- pkt 的 buffer 会被**复用**，所以**不能**把 pkt 直接推进队列！
  跨线程传递前必须先拷一份引用：
  ```c
  AVPacket *new_pkt = av_packet_alloc();
  av_packet_move_ref(new_pkt, pkt);   // 转移所有权（pkt 变空）
  // 或
  av_packet_ref(new_pkt, pkt);        // 增加引用（pkt 仍可用）
  ```

**规则 5：`ret >= 0` 表示成功拿到一个包，必须 continue 继续收**

不能拿到一个就 break —— 一次 `send` 可能产出多个包。

**规则 6：`frame == NULL` 只用于冲刷**

不要拿它当「送一个空帧」用。

### 【知识点 17】AVPacket 字段速查

| 字段 | 含义 |
| --- | --- |
| `data` / `size` | 编码后的裸 AAC 数据及字节数 |
| `pts` | 本包第一个采样点在时间轴上的位置（**单位 = 采样点**，不是秒） |
| `dts` | 解码时间戳；音频无 B 帧，通常 == `pts` |
| `duration` | 本包覆盖多少采样点（通常 == `frame_size`） |
| `flags` | `AV_PKT_FLAG_KEY` 等；AAC 每帧都是关键帧（`0x1`） |

分配与释放：

```c
AVPacket *pkt = av_packet_alloc();    // 不要用 av_init_packet（已废弃）
...
av_packet_free(&pkt);                 // 传二级指针，free 后置 NULL
```

## 6. 【知识点 22】PTS 与时间戳

### 6.1 PTS 回答什么问题

> 「这一帧的数据，是从整段音频的第几个采样点开始的？」

**单位是采样点，不是秒。** 换算：

```
秒 = pts / sample_rate
   = 1024 / 48000 = 0.02133 s     （第 2 帧的开始时间）
```

规则：**第 n 帧的 `pts = n × frame_size`，第一帧必须是 0。**

```c
frame->pts = pts;              // 先赋值（用本帧起点）
pts += frame->nb_samples;      // 再累加（准备下一帧起点）
```

> ⚠ **顺序写反是个常见 bug**：
> ```c
> pts += frame->nb_samples;
> frame->pts = pts;            // ✗ 第一帧就变成 1024，整体偏移 21 ms
> ```
> 裸 AAC 里看不出来（ADTS 没有全局时间轴），但封装进 mp4 后音画同步就整体偏了。

### 6.2 为什么单位是采样点而不是秒

整数运算无误差。用秒就只能存浮点，长时间播放会累积误差。
播放器知道 `sample_rate`，自己除一下就行。

### 6.3 AAC 的 priming 帧

编码器吐出的第一个包 `pts = -1024`（**负数，合法**）。

它不对应真实音频，是让解码端能正确重建开头 1024 个采样点的「预卷」数据
（因为 MDCT 需要前后文）。解码器会把它丢掉。

**所以看到负 pts 不要「修」它，这是规范行为。**

对应关系：`initial_padding = 1024` → 首包 `pts = -1024`。

### 6.4 实测时间轴核对

```
原始 PCM        : 481489 个采样点 = 10.031 s
送出            : 471 帧（470 个完整 1024 点帧 + 1 个 209 点尾帧）

编码器吐出的包  :
  正包 470 个   × duration 1024  = 481280
  priming 1 个  × duration 1024  =   1024     ← pts = -1024
  尾部 padding 1 个 × duration 209 =    209
  ─────────────────────────────────────────
  合计 472 个包                   = 482304 个采样点 = 10.048 s

差额 = 482304 - 481489 = 815
     = priming(1024) - 尾帧省下的部分(209)
```

**结论**：输入 481489 点，输出 482304 点，多出 815 点。
这 815 点不是 bug，而是 AAC 为了让解码端能正确重建开头而额外携带的信息
（priming 1024 点 减去 尾部本来就要补齐的 209 点）。

> `ffprobe` 报的文件时长（10.308 s）比 10.048 s 还大一点，
> 因为 ADTS 没有全局时长字段，ffprobe 是**按文件大小和码率估算**的，
> 会有偏差。要精确算时长应该数包数 × 1024 / sample_rate。

## 7. 【知识点 23】尾帧处理

文件总采样点数一般不是 1024 的整数倍，最后一块会短。
本项目：`481489 % 1024 = 209`。

两种处理方式：

| 方式 | 做法 | 后果 |
| --- | --- | --- |
| (a) 补零 | 不管读到多少都送 1024 个点，剩余补 0 | 简单，但末尾多一小段静音 |
| **(b) 按实际长度送** | 改 `frame->nb_samples` 为实际点数 | **本项目的做法**，时长严格一致 |

```c
int nb_samples_read = (int)(read_bytes /
        ((size_t)av_get_bytes_per_sample(cfg.in_sample_fmt) * (size_t)cfg.channels));
...
frame->nb_samples = nb_samples_read;   // 只描述真实存在的数据
```

> ⚠ **改了 `nb_samples` 之后物理容量没变**。`av_frame_get_buffer` 分配的
> 还是 1024 点的容量，只是「逻辑长度」改成 209。只要
> `nb_samples ≤ 容量`就是安全的 —— 这叫「缩小使用、不超用」。

**换算式（输入是 packed，所以要乘声道数）**：

```
采样点数 = 字节数 / (每采样点字节数 × 声道数)
```

**更通用的做法（实时采集必须用）**：用 `av_audio_fifo`

```c
AVAudioFifo *fifo = av_audio_fifo_alloc(sample_fmt, nb_channels, 1);

// 收到不固定长度的数据块，先写进 FIFO
av_audio_fifo_write(fifo, (void **)frame->data, nb_samples);

// 每次从 FIFO 取满 frame_size 个点送编码器
while (av_audio_fifo_size(fifo) >= frame_size) {
    av_audio_fifo_read(fifo, (void **)out_frame->data, frame_size);
    encode(ctx, out_frame, pkt, output, write_adts);
}
```

## 8. 【知识点 3】ADTS 头详解

### 8.1 为什么需要它

AAC 编码器输出的每个 packet 是**裸 `raw_data_block`**，里面没有任何帧同步信息
和格式信息。播放器拿到一串字节，既不知道从哪开始是一帧，也不知道采样率多少、
几个声道。

ADTS（Audio Data Transport Stream）就是给每个裸帧前面加一个头，
把这些信息重复携带一遍，让播放器能随机定位、随到随播。

### 8.2 位域分布（56 bit = 7 字节，无 CRC 时）

```
┌───────────────────────────────────────────────────────────────┐
│ syncword                 12 bit = 0xFFF  帧同步字，用于定位     │
│ ID                        1 bit = 0 (MPEG-4) / 1 (MPEG-2)     │
│ layer                     2 bit = 00     AAC 恒为 0           │
│ protection_absent         1 bit = 1      1=无CRC → 头长 7 字节 │
├───────────────────────────────────────────────────────────────┤
│ profile                   2 bit = audioObjectType - 1 (LC=1)  │
│ sampling_frequency_index  4 bit （见下表）                     │
│ private_bit               1 bit = 0                           │
│ channel_configuration     3 bit >7 时填 0，改用 PCE           │
├───────────────────────────────────────────────────────────────┤
│ original/copy             1 bit = 0                           │
│ home                      1 bit = 0                           │
│ copyright_id_bit          1 bit = 0                           │
│ copyright_id_start        1 bit = 0                           │
│ aac_frame_length         13 bit = AAC裸数据字节数 + 7          │
│ adts_buffer_fullness     11 bit = 0x7FF  (VBR 约定值)          │
│ number_of_raw_data_blocks 2 bit = 0      表示后面只有 1 个块   │
└───────────────────────────────────────────────────────────────┘
```

### 8.3 采样率索引表（AAC 规范固定，不能自己编号）

| 索引 | 采样率 | 索引 | 采样率 |
| --- | --- | --- | --- |
| 0 | 96000 | 7 | 22050 |
| 1 | 88200 | 8 | 16000 |
| 2 | 64000 | 9 | 12000 |
| 3 | **48000** | 10 | 11025 |
| 4 | 44100 | 11 | 8000 |
| 5 | 32000 | 12 | 7350 |
| 6 | 24000 | | |

### 8.4 代码对应

```c
adts_header[0] = 0xFF;
/* [1] = 1111 0001: syncword低4位(1111) + ID=0 + layer=00 + protection_absent=1 */
adts_header[1] = 0xF1;
/* [2] = profile(2bit) | 采样率索引(4bit) | channel_cfg 高2位 */
adts_header[2] = (ctx->profile << 6) + (freq_idx << 2) + (chan_cfg >> 2);
/* [3] = channel_cfg 低2位 | frame_length 高3位 */
adts_header[3] = ((chan_cfg & 3) << 6) + (frame_length >> 11);
/* [4] = frame_length 中间8位 */
adts_header[4] = (frame_length & 0x7FF) >> 3;
/* [5] = frame_length 低3位 | buffer_fullness 高5位(全1) */
adts_header[5] = ((frame_length & 7) << 5) + 0x1F;
/* [6] = buffer_fullness 低6位(全1) | raw_data_blocks(00) */
adts_header[6] = 0xFC;
```

### 8.5 两个边界检查

**`aac_frame_length` 只有 13 bit，上限 8191。**

正常 AAC 帧（1024 点 @128kbps）约 200~600 字节，本机实测 274~547 字节，
不会触及上限。但「外部输入必须校验」是编码器代码的基本素养：

```c
uint32_t frame_length = (uint32_t)aac_length + 7u;
if (frame_length > 0x1FFFu) {
    fprintf(stderr, "warning: aac frame too big\n");
    frame_length &= 0x1FFFu;
}
```

**`channel_configuration` 只有 3 bit，能表示 0~7。**

AAC 约定：**0 表示「声道配置由 PCE（Program Config Element）描述」**。
所以超过 7 声道时不能硬塞数字：

```c
uint8_t chan_cfg = ctx->ch_layout.nb_channels;
if (chan_cfg > 7)
    chan_cfg = 0;    // 表示要用 PCE
```

### 8.6 【知识点 5 / 15】`AV_CODEC_FLAG_GLOBAL_HEADER` 的语义

**含义**：告诉编码器「把全局头（对 AAC 是 `AudioSpecificConfig`）
从码流里挪出去，由封装层统一写一次」。

**对 AAC 的效果**：每个 packet 里只有裸 `raw_data_block`，**不带 ADTS**。

**为什么本项目要主动设这个 flag？**

| 编码器 | 默认行为 |
| --- | --- |
| native `aac` | 不带 ADTS |
| `libfdk_aac` | **带 ADTS** |

实测两者的 `ctx->flags` 都是 0，**没法靠 flags 区分谁带谁不带**。
所以主动置上这个 flag，让两边行为统一（都不带），再由程序自己补 ADTS，
输出就是一个 `ffplay` 能直接播的文件。

**注意事项**：必须在 `avcodec_open2()` **之前**设置，之后再改无效。

验证是否生效：`ctx->flags & AV_CODEC_FLAG_GLOBAL_HEADER`（本机实测值 `0x400000`）。

## 9. 【知识点 19 / 27】内存与生命周期

### 9.1 释放函数统一传二级指针

```c
av_frame_free(&frame);
av_packet_free(&pkt);
avcodec_free_context(&codec_ctx);
swr_free(&swr);
```

原因：它需要在 `free` 之后把调用方的指针置成 `NULL`，防止误用野指针。
C 语言里改调用方的指针只能靠传地址。

### 9.2 谁负责释放 ch_layout 里的内存

| 对象 | 谁负责 `uninit` |
| --- | --- |
| `codec_ctx->ch_layout` | `avcodec_free_context()` |
| `frame->ch_layout` | `av_frame_free()` |
| 自己声明的栈上布局 | **必须自己 `av_channel_layout_uninit()`** |

所以 `av_frame_free` / `avcodec_free_context` 之后**不需要**再手动 uninit，
但 `create_swr()` 里的 `in_layout` 必须自己 uninit。

### 9.3 goto cleanup —— C 项目里的标准写法

为了让「中途失败」的路径也能走到统一的释放代码：

```c
uint8_t *pcm_buf = malloc(...);
if (!pcm_buf) goto cleanup;
uint8_t *pcm_temp_buf = malloc(...);
if (!pcm_temp_buf) goto cleanup;

cleanup:
    if (infile)  fclose(infile);
    if (pcm_buf) free(pcm_buf);
    ...
```

避免每个 `exit(1)` 前面都抄一遍 free。

### 9.4 缓冲区生命周期对照表

| 缓冲区 | 谁分配 | 谁释放 | 生命周期要求 |
| --- | --- | --- | --- |
| `frame->data[]` | `av_frame_get_buffer` | `av_frame_free` | frame 存活期间 |
| `pkt->data` | 编码器内部 | 下一次 `receive` 或 `av_packet_free` | **只到下一次 receive** |
| `pcm_buf` | `malloc` | `free` | 到 `avcodec_send_frame` 返回后 |
| `in_layout` | 栈上 | `av_channel_layout_uninit` | 函数作用域内 |

## 11. 错误码速查

用 `av_strerror` 把负错误码翻译成可读字符串：

```c
char err[AV_ERROR_MAX_STRING_SIZE] = {0};   // 64 字节
av_strerror(ret, err, sizeof(err));
fprintf(stderr, "failed: %s\n", err);
```

| 错误码 | 常见原因 |
| --- | --- |
| `AVERROR(EAGAIN)` | **不是错误**：编码器需要更多输入 |
| `AVERROR_EOF` | **不是错误**：冲刷完毕 |
| `AVERROR(EINVAL)` | 参数非法（采样率/格式/布局不被支持）；或 `avcodec_open2` 参数冲突 |
| `AVERROR(ENOMEM)` | 内存不足 |
| `AVERROR(ENOENT)` | 找不到（如设备、文件） |

## 12. 常见坑清单

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| PTS 累加顺序反了 | 音画整体偏移 21 ms | `frame->pts = pts;` 然后再 `pts += nb` |
| 忘了 flush | 末尾约 21 ms 被截断 | 循环后 `encode(ctx, NULL, ...)` |
| 把 `EAGAIN` 当错误 | 第一次 send 就报错退出 | `EAGAIN`/`EOF` 都是正常流程 |
| 硬编码 1024 | 换编码器就崩 | 读 `ctx->frame_size` |
| 用 `linesize[1]` 算第 2 声道 | 读到垃圾值 | 平面字节数 = `nb_samples × 每点字节数` |
| 忘了 `av_frame_make_writable` | 编码结果错乱 | 每次写 frame 前都要调 |
| 按值赋值 `AVChannelLayout` | double free | 用 `av_channel_layout_copy` |
| 复用 `pkt->data` 跨线程 | 数据被覆盖 | `av_packet_ref`/`move_ref` 拷一份 |
| 尾帧补零 | 末尾多一段静音 | 按实际长度改 `nb_samples`；或用 `av_audio_fifo` |
| 拿 `swr_convert` 返回值当输入点数 | 数据错位 | 用返回值更新 `nb_samples` |
| `-rpath` 写含空格路径 | `ld: cannot find Files/...` | DLL 没有 rpath 语义，用 PATH 或拷 DLL |
| 负 PTS 当成 bug | 白改半天 | `pts = -initial_padding` 是规范行为 |

## 13. 进一步学习路线

### 13.1 用 libavformat 做封装

本程序手写 ADTS 是为了讲清编码本身。真实项目应该让 libavformat 负责容器：

```c
AVFormatContext *fmt_ctx = NULL;
avformat_alloc_output_context2(&fmt_ctx, NULL, NULL, "out.m4a");

AVStream *st = avformat_new_stream(fmt_ctx, NULL);
avcodec_parameters_from_context(st->codecpar, codec_ctx);   // ★ 关键：把编码参数传给流

avio_open(&fmt_ctx->pb, "out.m4a", AVIO_FLAG_WRITE);
avformat_write_header(fmt_ctx, NULL);

// 循环里用 av_interleaved_write_frame 替代 fwrite
av_packet_rescale_ts(pkt, codec_ctx->time_base, st->time_base);  // ★ 时间基转换
av_interleaved_write_frame(fmt_ctx, pkt);

av_write_trailer(fmt_ctx);
```

好处：

- **不用手写 ADTS** —— `avformat_write_header` 会自动生成 `AudioSpecificConfig`
- **时间基自动处理** —— 编码器的 `time_base` 和流的 `time_base` 通常不同
  （AAC 编码器是 `{1, sample_rate}`，mp4 流是 `{1, 1000000}` 之类），
  必须用 `av_packet_rescale_ts` 转换，这一步手写 ADTS 时接触不到但实际项目必踩
- 支持 mp4 / m4a / mkv / flv 等各种容器

容器选择建议：

| 容器 | 扩展名 | 说明 |
| --- | --- | --- |
| ADTS | `.aac` | 流式友好，每帧自带头，可随意截断 |
| MP4 / M4A | `.m4a` | 文件小，元数据丰富，但不能流式播放（moov 在尾部） |
| MKV | `.mka` | 灵活，适合多轨 |

### 13.2 实时采集

输入不再是文件而是设备（麦克风），每次拿到的采样点数不固定，必须用 `av_audio_fifo` 缓冲（见第 7 节）。

设备采集本身用 libavdevice：

```c
// Windows: dshow
avdevice_register_all();
const AVInputFormat *ifmt = av_find_input_format("dshow");
avformat_open_input(&fmt_ctx, "audio=麦克风名", ifmt, NULL);
// Linux: alsa / pulse
const AVInputFormat *ifmt = av_find_input_format("alsa");
```

### 13.3 变采样率

若源是 44100 而编码器要求 48000，直接在 `create_swr` 里：

```c
swr_alloc_set_opts2(&swr,
                    &enc_ctx->ch_layout, enc_ctx->sample_fmt, enc_ctx->sample_rate,  // 48000
                    &in_layout,          in_fmt,             44100,                  // 源
                    0, NULL);
```

swr 会自动做带抗混叠滤波的重采样。注意此时 `swr_convert` 的输入输出采样点数
**不成比例**，必须用返回值。
