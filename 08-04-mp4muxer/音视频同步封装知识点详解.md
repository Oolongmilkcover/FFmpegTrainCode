# 音视频同步封装知识点详解（08-04-mp4muxer）

> 配套源码：同目录 `main.cpp` / `videoencoder.cpp` / `audioencoder.cpp` /
> `audioresampler.cpp` / `muxer.cpp`
> 环境：Qt 6.11.0 (MinGW 13.1.0) + FFmpeg 8.1（libavformat 62 / libavcodec 62 / libavutil 60）
> 语言：C++17；构建：CMake

---

## 0. 这份示例的定位

前三个工程各讲一件事，08-04 把它们**组装成一个真正的转封装程序**，并回答
08-03 没讲透的那个问题：**两路流的时间戳怎么对上**。

```
   YUV 裸流 ──▶ VideoEncoder ──▶ H.264 包 ─┐
                                            ├─▶ Muxer ──▶ out.mp4
   PCM 裸流 ──▶ AudioResampler ─▶ AudioEncoder ─▶ AAC 包 ─┘
                (s16→fltp)
```

| 工程 | 主题 | 关键问题 |
| --- | --- | --- |
| 08-01 | 音频编码 | AAC 为什么只吃 fltp |
| 08-02 | 视频编码 | 视频的 time_base 与 pts |
| 08-03 | 封装 | 容器、交织、trailer |
| **08-04** | **同步封装** | **两条时间轴如何统一与调度** |

## 1. 模块划分

| 文件 | 职责 | 对应 pusher 的层 |
| --- | --- | --- |
| `videoencoder.*` | YUV → H.264 包 | `X264VideoEncoder` |
| `audioencoder.*` | PCM(fltp) → AAC 包 | `AacAudioEncoder` |
| `audioresampler.*` | s16 packed → fltp planar | 编码器内部的 swr |
| `muxer.*` | 建流/写头/交织写包/写尾 | `FormatMuxer` |
| `main.cpp` | 串联 + 音视频调度 | `Pusher` |

每个类的边界都遵循同一条原则：**只做一件事，自己不管理生命周期之外的时序**。
时间轴和调度全在 `main.cpp` 里，这样「同步逻辑」只有一处，改起来不会漏。

## 2. 统一时间轴：为什么用微秒

音频和视频的「自然时间基」不一样：

| | 一次处理多少 | 自然时间基 |
| --- | --- | --- |
| 音频 | 1024 个采样点 | `{1, 44100}`，一个单位 ≈ 22.7 µs |
| 视频 | 1 帧 | `{1, 25}`，一个单位 = 40 ms |

放在同一个 `while` 里比「谁更早」，必须先统一。本工程选 **`{1, 1000000}`（微秒）**：

```
audio_pts(µs) = 已送采样点数 / 44100 * 1000000
video_pts(µs) = 已送帧号     / 25    * 1000000
```

fps=25 时每帧前进 `1000000/25 = 40000` µs；AAC 每帧前进
`1024/44100*1000000 ≈ 23219.95` µs —— 两个数都不是整数倍关系，
所以**不能**用「一帧视频 = 多少帧音频」这种整数比例来同步。

> **另一种常见路线**：各用各的自然时间基（视频 `{1,fps}`、音频 `{1,sample_rate}`），
> 比较时用 `av_compare_ts(a, tb_a, b, tb_b)` 让它自动换算。
> 两种都行。统一微秒的好处是「累加 pts」只有一种写法、判断逻辑直观；
> 代价是 pts 数值大（5 秒 = 5,000,000），且必须处处记得换算。

### 2.1 一个精度提醒

本工程沿用了原版的 `double` 累加（`audio_pts += audio_frame_duration`）。
`double` 能精确表示 2^53 以内的整数，5 秒 = 5e6 完全没问题，
但它**每帧都会引入一次舍入**，长时间运行（几小时）会累积到毫秒级。

更稳的写法是用**绝对计数**推 pts，而不是累加：

```cpp
// 每轮用「已处理的数量」重新算，误差不累积
int64_t audio_pts_us = samples_written * 1000000LL / sample_rate;
int64_t video_pts_us = frame_index    * 1000000LL / fps;
```

## 3. 三处时间基转换（最容易漏的地方）

一个包从产生到落盘，时间戳要被换算**三次**：

```
① 调用方时间轴 ──▶ 编码器 time_base     （videoencoder.cpp / audioencoder.cpp）
   微秒            视频 {1,1000000}（恒等）
                   音频 {1,44100}

② 编码器 time_base ──▶ 流 time_base      （muxer.cpp 的 SendPacket）
   视频 {1,1000000}  → mp4 决定（实测仍给 1/1000000）
   音频 {1,44100}    → mp4 决定（实测仍给 1/44100）

③ 流 time_base ──▶ 容器内部刻度          （libavformat 自己做，不用管）
```

**每一步漏掉的后果**

| 漏了哪步 | 现象 |
| --- | --- |
| ① | 音频 pts 被当成采样点数直接塞给编码器，时间轴差 44100 倍 |
| ② | 包还是微秒/采样点，容器按自己的刻度解释 → 时长离谱、播放飞快 |

第 ② 步必须**现查 `st->time_base`**，不能在 `AddStream` 时缓存 ——
`avformat_write_header` 会改写它。

> **实测对比**：08-03 封 flv 时，mp4/flv muxer 把视频流时间基从 `{1,25}`
> 改成 `{1,1000}`（flv）或 `{1,12800}`（mp4，=25×512，为了整除）。
> 而 08-04 里视频编码器的时间基本来就是 `{1,1000000}`，已经足够细，
> muxer **直接沿用了**它。
> 结论：**不要假设容器会怎么改你的时间基**，永远现查现算。

## 4. 音视频交织调度

```cpp
while (!audio_finished || !video_finished) {
    const bool do_video = !video_finished &&
                          (audio_finished || audio_pts > video_pts);
    ...
}
```

判据一句话：**谁的时间戳更靠后，就先补谁**。

- `audio_pts > video_pts` → 音频跑前面了，这一轮处理视频（把视频追上来）
- `audio_pts <= video_pts` → 处理音频

原版把条件写成三段：

```cpp
(video_finish != 1 && audio_pts > video_pts) ||
(video_finish != 1 && audio_finish == 1)
```

逻辑等价，只是后者把「音频已结束 → 只能处理视频」显式列了一遍。
本工程整理成 `audio_finished || audio_pts > video_pts`，读起来更直观。

**为什么必须交替**：如果先把视频全部写完再写音频，音频的 dts 会从 0 开始，
相对已写入的视频包就是**倒退**，muxer 会报 `non-monotonous DTS`，
播放器 seek 也会乱。见 08-03 的【知识点 21】。

**为什么还要 `av_interleaved_write_frame`**：调度只保证「送进去的顺序大致交替」，
但两路的包不是严格 1:1，muxer 内部还会按 dts 再排一次。两重保险。

## 5. 冲刷（flush）的顺序

某一路读到文件末尾时，必须**立刻**冲刷它的编码器：

```cpp
if (video_finished) {
    video_encoder.Encode(nullptr, 0, ...);   // send(nullptr)，把残留包吐干净
}
```

不冲刷的后果：

| | 丢什么 | 现象 |
| --- | --- | --- |
| 视频 | x264 look-ahead 压住的若干帧 | 最后 0.1~0.2 秒画面卡住 |
| 音频 | AAC 内部 <1024 个采样点 | 最后一个音被切断 |

**两路的结束是独立的**：本示例里音频 215 帧（5.016 s）、视频 125 帧（5.040 s），
谁先读完谁先冲刷，另一路继续跑，直到两路都 `finished`。

## 6. FFmpeg 4.2.1 → 8.1 改动清单

本工程原版是 FFmpeg 4.2.1，以下改动**不改就编译不过**：

| # | 4.2.1 写法 | 8.1 写法 |
| --- | --- | --- |
| 1 | `AVCodec *codec = avcodec_find_encoder(...)` | `const AVCodec *codec = ...` |
| 2 | `ctx->channels = n` | 字段删除 → `ctx->ch_layout.nb_channels` |
| 3 | `ctx->channel_layout = av_get_default_channel_layout(n)` | `av_channel_layout_default(&ctx->ch_layout, n)` |
| 4 | `av_get_default_channel_layout(n)` | **函数已删除** |
| 5 | `frame->channels` / `frame->channel_layout` | 字段删除 → `frame->ch_layout` |
| 6 | `swr_alloc_set_opts(ctx, uint64掩码, ...)` | **函数已删除** → `swr_alloc_set_opts2(&ctx, &out_layout, ..., &in_layout, ...)` |

对照原版代码看最直观：

```cpp
// 原版 audioencoder.cpp
codec_ctx_->channels       = channels_;
codec_ctx_->channel_layout = av_get_default_channel_layout(codec_ctx_->channels);

// 本版
av_channel_layout_default(&codec_ctx_->ch_layout, channels_);
```

```cpp
// 原版 audioresampler.cpp
ctx_ = swr_alloc_set_opts(ctx_,
                          av_get_default_channel_layout(out_channels_),  // 函数没了
                          AV_SAMPLE_FMT_FLTP, out_sample_rate_,
                          av_get_default_channel_layout(in_channels_),   // 函数没了
                          AV_SAMPLE_FMT_S16, in_sample_rate_,
                          0, NULL);

// 本版
AVChannelLayout in_layout{}, out_layout{};
av_channel_layout_default(&in_layout, in_channels_);
av_channel_layout_default(&out_layout, out_channels_);
swr_alloc_set_opts2(&ctx_, &out_layout, AV_SAMPLE_FMT_FLTP, out_sample_rate_,
                           &in_layout,  AV_SAMPLE_FMT_S16,  in_sample_rate_,
                           0, nullptr);
av_channel_layout_uninit(&in_layout);
av_channel_layout_uninit(&out_layout);
```

除了这些「硬」改动，还有 C 风格到 C++17 的整理：`#define` → `constexpr`、
`NULL` → `nullptr`、`printf` → `std::printf`、`%lld` → `PRId64`、
`malloc/free` → `std::vector`、`FILE*` → `std::unique_ptr<FILE, FileCloser>`。

## 7. 转换时修掉的三个 bug

### 7.1 编码出错时会往容器里塞 NULL 指针（崩溃）

```cpp
// 原版 videoencoder.cpp / audioencoder.cpp
while (1) {
    AVPacket *packet = av_packet_alloc();
    ret = avcodec_receive_packet(codec_ctx_, packet);
    packet->stream_index = stream_index;
    if (ret == AVERROR(EAGAIN) || ret == AVERROR_EOF) {
        ret = 0;
        av_packet_free(&packet);     // packet 变 NULL
        break;
    } else if (ret < 0) {
        av_packet_free(&packet);     // packet 变 NULL
        ret = -1;                    // ← 没有 break！
    }
    packets.push_back(packet);       // ← 把 NULL 塞进容器
}
```

后面 `SendPacket(NULL)` 第一行就 `packet->stream_index` → 空指针崩溃。
本版改成「出错就 free + break，绝不 push」，并把 `stream_index` 的赋值挪到确认成功之后。

### 7.2 `SendPacket` 先解引用再判空

```cpp
// 原版 muxer.cpp
int Muxer::SendPacket(AVPacket *packet)
{
    int stream_index = packet->stream_index;   // ← packet 可能是 NULL
    ...
    if(!packet || packet->size <= 0 || !packet->data) { ... }
```

判空必须在最前面。本版已调整。

### 7.3 用 `avformat_close_input` 关闭**输出**上下文

```cpp
// 原版 muxer.cpp
void Muxer::DeInit()
{
    if(fmt_ctx_) {
        avformat_close_input(&fmt_ctx_);   // ✗ 这是解封装用的
    }
}
```

`avformat_close_input` 会按 **AVInputFormat** 去释放 demuxer 的私有数据，
而 `fmt_ctx_` 是 `avformat_alloc_output_context2` 建出来的**输出**上下文 ——
用错函数属于未定义行为（轻则泄漏，重则崩溃）。

而且原版 `Muxer::~Muxer()` 是空的，`DeInit` 从来没被调用过，
`avio_open` 打开的句柄一直没关。

正确的输出侧收尾：

```cpp
if (fmt_ctx_) {
    if (fmt_ctx_->pb && !(fmt_ctx_->oformat->flags & AVFMT_NOFILE))
        avio_closep(&fmt_ctx_->pb);     // 先关 IO（会 flush 缓冲）
    avformat_free_context(fmt_ctx_);    // 再释放上下文
}
```

本版还在析构里兜底调一次 `DeInit`，并把它做成幂等的。

### 7.4 顺带修的：文件大小读不到

第一版在 `av_write_trailer()` 之后立刻用 `std::filesystem::file_size()` 查输出大小，
结果永远是 **0 字节** —— 因为数据还在 `AVIOContext` 的缓冲里，
要等 `avio_closep` 才真正落盘。

修法：trailer 之后显式 `mp4_muxer.DeInit()`（幂等），再读文件大小。

## 8. 实测结果

测试素材：`sound_in_sync_test.mp4`（720×576 / 25fps / 44.1kHz 立体声 / 40 秒），
用 `fetch_test_media.bat` 取前 5 秒生成裸 YUV + 裸 PCM。

```
VideoEncoder    : 720x576 @25fps, 500kbps, time_base=1/1000000
AudioEncoder    : 44100Hz 2ch 128kbps, frame_size=1024, time_base=1/44100
AudioResampler  : s16/2ch/44100Hz -> fltp/2ch/44100Hz
Muxer           : out.mp4 (容器=mp4)
  流0 最终 time_base = 1/1000000
  流1 最终 time_base = 1/44100
```

产物校验：

| 项 | 值 |
| --- | --- |
| 视频 | h264 / 720×576 / 25fps / 125 个包 / 4.96 s |
| 音频 | aac / 44100 Hz 立体声 / 216 个包 / 4.99 s |
| 容器 | mp4，4.992 s，**92.38 KB**，bit_rate 151 kbps |
| 解码 | `ffmpeg -i out.mp4 -f null -` 返回 **0** |
| 时间轴差 | **−0.024 s**（音 − 视，小于 1 帧 = 0.04 s，属正常） |

> 输入 YUV 是 125 帧（5.040 s 时间轴），PCM 是 5.016 s。
> 两条流长度天然差一帧以内 —— 这才是「同步正常」的样子。
> 如果差到秒级，就是 3 处时间基转换漏了某一步。

## 9. 踩坑清单

| # | 坑 | 现象 | 正解 |
| --- | --- | --- | --- |
| 1 | **PATH 上有别的 MinGW** | 程序一行没执行就退出，退出码 `0xC0000139`（ENTRYPOINT_NOT_FOUND） | 静态链接 `-static-libgcc -static-libstdc++`，并把编译器自带的 `libwinpthread-1.dll` 拷到 exe 旁 |
| 2 | 写包后读 `pkt->pts` | 显示 0 / NOPTS | `av_interleaved_write_frame` 成功后会把包清零，要打印的字段提前存 |
| 3 | 缓存 `st->time_base` | 换算用错刻度 | `av_write_trailer` 之前的任何时刻都可能被改写，**现查** |
| 4 | 漏写 trailer | mp4 无法播放（缺 moov） | 必调，且在关闭编码器之前 |
| 5 | 用 `avformat_close_input` 关输出上下文 | 未定义行为 | `avio_closep` + `avformat_free_context` |
| 6 | 编码出错时 `push_back(NULL)` | 空指针崩溃 | free + break，不 push |
| 7 | 尾帧不足一帧 | 尾部丢弃（本工程选择丢弃） | 想精确保留就用 `av_audio_fifo` 攒够再送 |
| 8 | `av_get_default_channel_layout` | 编译报错（函数已删除） | `av_channel_layout_default` |
| 9 | `swr_alloc_set_opts` | 编译报错（函数已删除） | `swr_alloc_set_opts2` |
| 10 | 写完 trailer 立刻查文件大小 | 读到 0 字节 | 先 `avio_closep`（或显式 DeInit）再查 |

### 9.1 关于 `0xC0000139` 这个坑的完整分析

这是本次改造最花时间的一个问题，值得单独说清楚。

**现象**：`mp4muxer.exe` 编译零警告通过，但一运行就退出，
退出码 `-1073741511` = `0xC0000139` = `STATUS_ENTRYPOINT_NOT_FOUND`，
连 `main()` 的第一行 `printf` 都没执行（日志文件是空的）。

**排查过程**：

1. 先确认 FFmpeg 的 7 个 DLL 都在 build 目录 → 都在
2. 用同一 shell 跑 08-03 的 exe（同样的 FFmpeg 依赖）→ **正常**
3. `objdump -p` 对比两个 exe 的导入表 → 都依赖
   `libstdc++-6.dll` / `libgcc_s_seh-1.dll`
4. 看 PATH：`C:\mingw64\bin`（GCC **15.2**、**win32** 线程模型）排在
   `C:\Qt\Tools\mingw1310_64\bin`（GCC **13.1**、**posix** 线程模型）**之前**
5. 决定性实验：把 GCC 13.1 的 `libstdc++-6.dll` + `libgcc_s_seh-1.dll`
   拷到 exe 同目录 → **立刻能跑**

**根因**：exe 是用 Qt 的 MinGW 13.1 编的，但运行时按 PATH 顺序加载到了
`C:\mingw64` 的 GCC 15.2 运行时。两者线程模型不同（posix vs win32），
导出的符号集合不一致，exe 需要的某个入口点在 15.2 的 DLL 里找不到。

**为什么 08-01/02/03 没暴露**：它们用到的 libstdc++ 符号少（没有
`<filesystem>`、没有 `<memory>` 的 reset 之类），恰好 15.2 都提供。
08-04 用了 `<filesystem>` + `std::unique_ptr` 自定义删除器，才撞上。

**修法（已应用到四个工程）**：

```cmake
if(MINGW)
    target_link_options(<target> PRIVATE -static-libgcc -static-libstdc++)
    # posix 线程模型的 libstdc++ 还会用到 libwinpthread，拷配套版本过来
    get_filename_component(_mingw_bin_dir "${CMAKE_CXX_COMPILER}" DIRECTORY)
    add_custom_command(TARGET <target> POST_BUILD
        COMMAND ${CMAKE_COMMAND} -E copy_if_different
                "${_mingw_bin_dir}/libwinpthread-1.dll"
                "$<TARGET_FILE_DIR:<target>")
endif()
```

> 试过 `-Wl,-Bstatic -lwinpthread` 想把它也静态掉，但 GNU ld 是**从左到右**
> 解析的，那句出现在 `libstdc++` 之前时引用还没出现，等于没生效（实测仍动态依赖）。
> 所以改成「拷配套 DLL」这条更可靠的路。

## 10. 与 pusher 的关系

| 本工程 | pusher 里 |
| --- | --- |
| `VideoEncoder` | `X264VideoEncoder`（加 preset/tune/zerolatency，输入是采集的微秒） |
| `AudioEncoder` | `AacAudioEncoder` |
| `AudioResampler` | 编到 `AacAudioEncoder` 内部（设备给 s16，AAC 要 fltp） |
| `Muxer` | `FormatMuxer`（多一层 `rw_timeout` / `AVIOInterruptCB` / 断线重连） |
| `main` 的 while 循环 | `Pusher` 里拆成**三条线程 + 有界队列** |
| 读文件模拟采集 | 真正的 `dshow` / `alsa` 采集 |

### 本工程刻意简化掉的东西（真实推流必须补）

1. **没有网络超时**：`avio_open2` 要设 `rw_timeout`（微秒），否则断网会卡死
2. **没有中断回调**：`AVIOInterruptCB` 让「关窗口」能立刻打断阻塞中的写
3. **没有重连**：muxer 写失败要销毁重建，并重发关键帧
4. **没有实时节流**：用文件模拟采集，喂帧是「能跑多快跑多快」；
   真实采集必须按 fps 节奏喂，否则编码器队列会堆积或饥饿
5. **音视频同线程串行编码**：实时场景要拆线程，否则一路慢就拖累另一路
6. **尾帧直接丢弃**：专业做法用 `av_audio_fifo` 攒够一帧再送
